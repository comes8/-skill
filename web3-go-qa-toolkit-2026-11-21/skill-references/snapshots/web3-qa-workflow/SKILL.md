# Web3 测试工作流

先确认产品、模块、变更单、版本、接口/WebSocket/链上约定、目标环境与已有资产。不明确的规则标待确认，保留来源。用户只要求出覆盖范围时停在覆盖评审。收到明确批准的测试范围时依次完成用例、数据、计划和执行证据。读取 [测试设计](references/design.md) 中相关模块和实际核对口径，按 [工作台接入](references/workbench.md) 登记阶段。

1. **覆盖评审**：从变更影响、资金风险、核心链路、异常、状态转移、跨服务一致性、观测与恢复推导覆盖项。每项写可验证预期、来源、核对方式、优先级及待确认点。确定性样例也要标清适用环境。未获确认的规则不得转为预期。
2. **测试用例**：给用例稳定 ID，关联覆盖项与需求。小测 XMind 脚本可继续出脑图，保留结构化用例和矩阵供追溯。有跨接口依赖，列出每步抽取字段、后续请求怎么用及失败后的阻塞范围。金额用 Decimal 或整数最小单位核对。对异步系统分开验证受理、终态与下游收敛。
3. **准备数据**：优先团队已有夹具或授权环境里的数据接口。登录和输入等只能在页面做的准备步骤，由浏览器验证并记录数据 ID；再用 API 或另一观察源确认就绪。数据计划记录测试账号/钱包的引用、初始快照、隔离边界、并发限制、清理及复测方法，文件中省略实际密钥。
4. **安排执行**：简单接口探查用已批准的项目客户端或 curl。复用团队 Postman 集合时继续在其 Runner/CLI 跑。可重复的跨接口断言用项目 pytest，小测场景导出适用于轻量 HTTP 链路。浏览器用于面向用户的 UI 和证据，长期自动化沿用团队框架。JMeter/k6 用于单独有负载目标的性能任务。根据状态依赖串行，数据隔离后才并行。
5. **执行与复测**：区分测试环境和生产，动作受既有授权范围约束。只对获准环境发请求，执行有副作用步骤前核对或确认目标、账户和清理方案。提交超时先按原 ID 查状态，避免盲目重试。将版本、环境、用例 ID、通过/失败/阻塞、关键前后值及证据登记到工作台。报告只说明实际验证的范围。复测保留原失败证据和新的运行编号。

当正在编写而未写盘时用 `working`，已有产物待用户审阅时用 `review`。用例、数据、计划与执行证据都可作为独立阶段展示。
